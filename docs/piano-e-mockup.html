Gli Unit Test di MyoLogic Pro in un unico posto

Oggi catalogo, esiti e report vivono nel file Excel MyoLogic Pro – Unit Test v.2.1_rev00, dove lo stesso elenco di 264 test è copiato in 5 fogli. Il software proposto tiene il catalogo una volta sola, registra gli esiti per sessione di test e calcola da solo il report di rilascio. Ogni elemento si può creare, modificare ed eliminare.

Cosa c'è oggi nel file

Il file ha 7 fogli. Quattro sono copie identiche del catalogo (colonne A–K) con in più le colonne ESITO e NOTE per una configurazione hardware.

  • Cover&HistoryAutore, 2 approvatori, storico di 32 revisioni dal 15/06/2020 al 20/09/2026
  • Unit TestCatalogo master, 264 righe, senza esiti
  • AH03 + rotatore + PRISM + PulseCopia del catalogo + ESITO/NOTE
  • AH03 + coaxial plug 6 bande + 2Copia del catalogo + ESITO/NOTE
  • Conn.Remota ProiOS-AH02AH03+rotCopia del catalogo + ESITO/NOTE
  • Conn.Remota ProAndroid-AH02AH03Copia del catalogo + ESITO/NOTE
  • Esito TestRiepilogo finale scritto a mano

Gerarchia: 32 unità del software → 148 casi d'uso → 264 test. Ogni test ha Device, ID Test, Nome Test, Descrizione test e Descrizione operazioni. Unità e Caso d'uso sono celle unite su più righe.

Cosa non funziona e il software risolve

  • 5×Lo stesso catalogo è copiato in 5 fogli. Correggere un test vuol dire modificarlo 5 volte, e nulla garantisce che le copie restino uguali.
  • 95test senza ID. Gli ID 103, 152 e 167 sono usati più volte (167 tre volte).
  • 6modi diversi di scrivere l'esito, per esempio "NOT AVAILABLE " con uno spazio in fondo e "NOT PASSED (lato grafico)". 19 esiti sono vuoti.
  • 28test senza dispositivo indicato; " PRISM" compare con uno spazio davanti.
  • 3coppie di unità con nomi quasi uguali, per esempio "Gestione Dispostiivi" e "Gestione Dispositivi".
  • 12esiti NOT PASSED nei fogli, mentre Esito Test riporta "Tutti i test sono PASSED" e la versione v.2.0.1 per il test della v2.1. Il riepilogo non è collegato ai dati.
  • 6colonne (R–W: Esito Demo, Note Test RUSSO, Note Test ITA…) vuote in tutti i fogli.

Creazione, modifica, cancellazione

Nessuna cancellazione fa sparire esiti già registrati. Un test con risultati viene archiviato: esce dalle nuove sessioni ma resta nei report passati. Ogni eliminazione chiede conferma.

Le schermate

Sette schermate disegnate con la palette indicata: sfondo #E9EFF4, primario #254A6A, secondario #292D38 per la barra superiore e il testo. Numeri, nomi dei test e note vengono dal file; tester, orari e stati delle sessioni sono di esempio. Su schermi stretti ogni schermata scorre in orizzontale.

Sei fasi, ognuna con qualcosa da provare

Si parte dai dati, perché tutto il resto si appoggia lì. Alla fine di ogni fase c'è una versione funzionante da provare prima di passare alla successiva.

  1. Fase 1

    Fondamenta e import dei dati

    • Progetto Node.js e progetto Supabase. Tabelle Postgres con il modello descritto sopra, create da migrazioni SQL versionate.
    • Login con Supabase Auth.
    • Script di import in Node dal file Excel: riempie le celle unite di Unità e Caso d'uso, riporta gli esiti alle 4 forme standard, pulisce i nomi dei dispositivi, assegna gli ID mancanti, importa le 4 sessioni, le 32 revisioni, autore e approvatori.
    • Report di import con l'elenco di ogni correzione, da controllare insieme.

    Verifica: i conteggi nel database coincidono con il file (264 test, 335 PASSED, 12 NOT PASSED, 4 NOT AVAILABLE).

  2. Fase 2

    Catalogo test

    • Mockup 2 e 3: albero Unità → Caso d'uso → Test, ricerca, filtro per dispositivo.
    • Crea, modifica, duplica, archivia ed elimina per unità, casi d'uso, test e dispositivi, con le regole di sicurezza sulle eliminazioni.

    Verifica: modificare un test lo aggiorna in tutte le sessioni.

  3. Fase 3

    Release, configurazioni e sessioni

    • Gestione delle release (storico revisioni, autore, approvatori) e delle configurazioni.
    • Mockup 4 e 5: nuova sessione dai dispositivi in prova; esecuzione con esito, nota, tasti rapidi e salvataggio automatico.

    Verifica: una sessione completa registrata solo da tastiera.

  4. Fase 4

    Dashboard, report e notifiche

    • Mockup 1 e 6: copertura per unità, NOT PASSED aperti raggruppati per test, report calcolato con testi modificabili e invio agli approvatori.
    • Mockup 7: notifiche nell'app per nuovo NOT PASSED, sessione chiusa e report da approvare, create da trigger nel database.

    Verifica: il report della v.2.1 riporta gli stessi numeri del file; ciascuno dei 3 eventi crea la notifica per le persone giuste.

  5. Fase 5

    Export

    • Export Excel con la struttura del file attuale: Cover&History, Unit Test, un foglio per sessione, Esito Test.
    • Report in PDF tramite la stampa del browser.

    Verifica: esportare e reimportare il file restituisce gli stessi dati.

  6. Fase 6

    Collaudo e consegna

    • Test automatici su import, calcolo degli esiti ed export.
    • Prova completa insieme su una sessione reale.
    • Istruzioni per avvio, configurazione di Supabase e backup.

    Verifica: un tester nuovo esegue una sessione senza aiuto.

Tecnologia

Applicazione web
Si usa dal browser: nessuna installazione per chi esegue i test, tutti lavorano sugli stessi dati.
Node.js + Express
Pagine generate dal server (EJS) con htmx per le azioni rapide, come l'esito con un clic. Nessun framework frontend da mantenere (decisione 7).
Supabase
Database Postgres gestito, che il server Node interroga direttamente in SQL, e login degli utenti con Supabase Auth. Le tabelle nascono da migrazioni SQL salvate nel progetto.
exceljs
Lettura del file attuale ed export Excel con lo stesso layout, celle unite comprese.

L'app si avvia con npm start. La stringa di connessione al database e la chiave pubblica di Supabase stanno in un file di configurazione sul server: il browser non parla mai direttamente con il database.

Il piano gratuito di Supabase mette in pausa i progetti inattivi e non prevede backup automatici, quindi per l'uso reale conviene il piano Pro. Verifichiamo le condizioni al momento dell'attivazione.

Da decidere prima di partire

Queste scelte cambiano il lavoro delle prime fasi. Per ognuna c'è un'opzione consigliata; se va bene, basta confermare.

  1. Dove girano app e database?

    • Supabase cloud (regione UE) + app Node su un servizio di hosting consigliata
    • Supabase cloud (UE) + app Node su server aziendale
    • Tutto su server aziendale, con Supabase self-hosted

    Con il database già in cloud, mettere in cloud anche l'app evita di gestire un server e permette di lavorare da qualsiasi sede. La regione UE tiene i dati in Europa.

  2. Come si accede?

    • Email e password con Supabase Auth consigliata
    • Account Google o Microsoft aziendale

    Con il database raggiungibile in rete il login è obbligatorio, e dà a ogni esito un autore certo. Supabase Auth gestisce entrambe le opzioni.

  3. Teniamo lo storico delle modifiche?

    • Sì: chi ha cambiato cosa e quando consigliata
    • No

    Per la documentazione di validazione del software è utile poter dimostrare chi ha modificato un test o un esito. In Postgres basta un trigger per tabella: costa poco se si decide adesso.

  4. Come trattiamo gli ID dei test?

    • Tengo gli ID attuali e assegno 168–266 ai 95 test senza ID e ai 4 duplicati consigliata
    • Rinumero tutto da 1 a 264

    Tenere gli ID attuali evita di rompere i riferimenti già usati in documenti e conversazioni.

  5. Uniamo le unità con nomi quasi uguali?

    • Sì, con la tua conferma nel report di import consigliata
    • No, restano separate

    Coppie trovate: "Gestione account (TO)" / "Gestione Account TO", "Gestione Dispostiivi" / "Gestione Dispositivi", "Gestione account Distributore" / "Gestione account (DIS)".

  6. Che formato deve avere l'export Excel?

    • Stesso layout del file attuale consigliata
    • Tabella semplice

    Lo stesso layout mantiene la continuità con la documentazione già consegnata.

  7. Come costruiamo l'interfaccia?

    • Pagine generate da Node (EJS + htmx) consigliata
    • App React, per esempio con Next.js

    Le schermate dei mockup sono tabelle e form: le pagine generate dal server bastano e richiedono meno codice da mantenere. React conviene se in futuro serviranno interfacce molto più interattive.

  8. Chi riceve le notifiche di NOT PASSED e sessione chiusa?

    • Autore e approvatori della release consigliata
    • Tutti gli utenti

    "Report da approvare" va comunque solo agli approvatori. Autore e approvatori si scelgono tra gli utenti nella scheda della release.

Fuori dalla prima versione

  • Colonne R–W (Esito Demo, Note Test RUSSO, Note Test ITA): oggi sono vuote. Le note in più lingue si aggiungono dopo, se servono.
  • Allegati e screenshot sugli esiti.
  • Firma elettronica del report: si registrano nome, ruolo e data dell'approvatore.
  • Collegamento a un sistema di bug tracking.
  • Notifiche via email, Teams o Slack: nella prima versione arrivano solo dentro l'app.
  • App mobile dedicata: l'applicazione web si usa anche da tablet.
